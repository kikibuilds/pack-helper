# 开发总结

发货助手是给小卖家用的「把打包发货外包给同事」的工具：老板（或远程指令）在电脑上把各平台待发货的订单和预付面单收齐，生成一个发货文件发给打包的同事；同事不需要任何平台账号，照着打包清单拣货、打包、贴面单，做完把发货结果发回来。

## 1. 要解决的问题

- 同时在 Poshmark、Mercari、Depop（还有 eBay、Etsy、Shopify）卖货，每个平台的待发货订单、面单都要分别登录下载，很费时间。
- 想把拣货、打包、贴面单交给员工，但**不想给员工任何平台的账号权限**。
- 员工最少需要的信息：每个包裹装哪些商品（图片 / 商品名 / SKU / 数量）和对应的面单。
- 人不一定在电脑旁（甚至可能在国外），需要能远程启动、远程知道结果。

范围（当前）：Poshmark、Mercari、Depop 这三个**平台出预付面单**的国内订单，加上 Whatnot（面单在 Whatnot 上生成，买家付运费）。

## 2. 整体架构

```
┌──────────────── Mac（一直开着，Chrome 里登录着三个平台）────────────────┐
│                                                                        │
│  Chrome 扩展（Manifest V3）                                            │
│   ├ 批次页 batch.html ── 一键拉取 → 表格检查/修改 → 打包下载 / 打包并发邮件 │
│   ├ lib/autorun.js ──── 依次打开各平台待发货列表 → 逐单读取 → 抓面单       │
│   ├ lib/extract.js ──── 注入平台页面运行：读订单、找面单按钮、页面诊断      │
│   ├ lib/package.js ──── 打包清单 + 合并面单 PDF + 使用说明 → zip           │
│   ├ lib/remote.js ───── 定时让邮件程序查收件箱，执行远程指令               │
│   └ background.js ───── 截获面单下载、定时器                              │
│           │  Chrome Native Messaging（4 字节长度 + JSON）                 │
│           ▼                                                            │
│  邮件程序 mailer/send_packages.py（Python 标准库）                      │
│   ├ send：Gmail SMTP 发信（465 → 587 自动重试），带附件 / 密送 / 回复     │
│   ├ poll：Gmail IMAP 只读邮件头，找白名单 + 暗号的指令邮件                 │
│   └ 密码：macOS 钥匙串（install.sh 存入）                                │
└────────────────────────────────────────────────────────────────────────┘
          │ 发货邮件（zip 附件）                 ▲ 指令邮件「暗号 打包」
          ▼                                     │
     打包同事：解压 → 打印面单 → 照打包清单打包 → 生成发货结果发回
```

关键技术点：

- **读页面而不是用 API**：三个平台都没有给小卖家的开放 API，所以在用户自己已登录的 Chrome 里打开卖家后台读取（和市面上的 cross-listing 工具一样）。
- **抓面单的几种情况**：普通链接下载、`blob:` 链接（在页面 MAIN world 里替换 `URL.createObjectURL` 截获）、新标签页打开的 PDF、HTML 页里嵌入的 PDF、Poshmark「Download」弹窗里的第二个 Download 按钮、Mercari 订单页的「Open label」。
- **Depop**：列表页「To ship」每一行就有 SKU、图片和「Download shipping label」，直接在列表上处理；Depop 没有商品标题，用 `nethook.js` 截获页面自己的 JSON，按图片 ID 找到商品描述的第一行当商品名。
- **Mercari**：商品在订单页右侧「Order summary」里；再读一次商品页的 `og:title` / `og:image` 补全被截断的商品名和图片。
- **合并面单**：用 pdf-lib 把所有面单按编号顺序合成一个 PDF，每张面单前插一张同尺寸的纯文字「对照卡」（热敏打印机打不了图片）。
- **zip**：自己写的 STORE 模式 zip（无需依赖）。
- **发邮件**：扩展通过 Native Messaging 直接调用 Mac 上的 Python 程序，当场拿到成功 / 失败结果，页面显示「正在打包 → 正在发送 → 发送成功 / 失败（原因）」。
- **远程指令**：扩展每 1～10 分钟让邮件程序用 IMAP 查一次 Gmail 收件箱（只读邮件头）。只执行「白名单邮箱 + 标题带暗号 + 通过 Gmail 发件人验证（DKIM/DMARC）+ 3 小时内」的指令；插件自己发的信带 `X-PackHelper` 标记，不会被当成指令（防止自己给自己发时死循环）。

## 3. 迭代过程（按问题 → 解决）

### 阶段一：基础流程（V0.1.x）
1. **逐单读取**：在订单页点扩展图标「读取当前订单页」→ 订单进批次 → 打包成 zip（拣货单 HTML/CSV + 面单）。
2. **一键拉取**：依次打开三个平台的待发货列表，逐单读取、抓面单；带「停止」按钮；只拉一个平台的下拉菜单。
3. **不重复**：打包过的订单记 45 天，再拉取时标「之前打包过」、默认不勾选；缺面单的不算已打包，补上面单后进入下一个发货文件。
4. **已发货排除**：Mercari「Awaiting rating from buyer」等状态视为已寄出，不再打包。
5. **先检查再打包**：拉取不再自动打包，结果显示在表格里（面单「✓ 已对应 / 缺面单 + 原因 + 订单页链接」），可以改商品名 / SKU / 数量、拖入面单，改过的字段重新拉取时保留。
6. **对照卡**：热敏打印机打不了图片 → 对照卡改成纯文字（大号编号 + SKU + 数量 + 商品名），商品多时自动分页。
7. **Excel 把「1/2」变成日期** → 改成「第1件/共2件」。
8. **版本号**：zip 文件名和扩展里都显示版本号。
9. **隐私**：插件里不出现任何个人邮箱；示例一律用 example@gmail.com。

### 阶段二：发邮件（V0.1.22～V0.1.28）
- 旧方案是 launchd 监视下载文件夹再发信，但用户改过 Chrome 下载位置导致监视不到，而且扩展不知道有没有发成功 → **改成 Native Messaging**，页面实时显示状态和错误原因，失败可「重新发送」。
- Mac 自带 bash 3.2：变量后面紧跟中文全角括号会读错 → 脚本里变量全部写成 `${VAR}`。
- `cp` 复制下载文件时连带复制隔离属性被拒绝 → 改成只复制文件内容。
- 解压后的文件夹固定叫 `pack-helper`，直接覆盖更新，Chrome 里的设置和已打包记录不会丢。
- 邮件正文精简成给员工看的「几个包裹 + 三步做法」，标题和正文支持模板占位符（`{日期}` `{包裹数}` `{件数}` `{附件}` `{缺面单提醒}` `{包裹清单}`），设置里实时预览。
- 加「密送（BCC）」，老板可以悄悄收一份确认发出。
- TLS 握手超时 → 连接阶段自动重试 4 次（465 / 587 端口轮换），真正发信只做一次，避免重复发。

### 阶段三：远程指令（V0.2.0～V0.2.7）
- 讨论过手机 App 和邮件触发，选了**邮件触发**：手机自带邮件 App 就是遥控器，不用额外开发；在国内也可以用 QQ / 163 邮箱发指令。
- 指令：`暗号 打包`（全部平台重新拉取 → 打包 → 发邮件）、`暗号 拉取`（预览会打包哪些，不发邮件）、`暗号 状态`、`暗号 重发`。每封指令先回「收到」，做完回结果，接在同一个邮件对话里。
- 安全：白名单 + 暗号 + 只认 Gmail 自己加的那条发件人验证结果（防伪造）+ 3 小时有效 + 每封只执行一次；暗号太短（如 `SHIP` 会匹配 Shipping）时提醒。
- 发件邮箱自己给自己发指令：回信带标记跳过、回信标题去掉暗号，避免死循环和误触发。
- 远程打包默认「全选」：批次里有面单的全部打包，包括之前打包过的，回信里单独列出来提醒确认。
- 文案统一：「发货包」→「发货」，「发给员工」→「发邮件」。

### 阶段四：Mercari 和打包清单（V0.2.1～V0.2.9）
- Mercari 商品在订单页侧栏里，被通用规则排除，读成了「Send this order」→ 专门读「Order summary」里的商品链接 + 商品页补全。
- 商品名里方括号的编号自动当 SKU（`… Romper [MXM-27]`）。
- 打包过、但清空批次后重新建的行没有面单 → 只要还没有面单就去抓。
- 「已打包」标记可以手动去掉（表格里和「上次打包」列表里都可以）。
- **打包清单重做**（先出设计稿确认再写代码）：去掉拣货汇总，只按包裹列；每件商品「已拣货 / 缺货」、每个包裹「已打包 / 有问题」、员工备注、订单号链接、「打开面单」相对路径链接；勾选自动保存；「完成，生成发货结果」把需要处理的排在上面、已打包的折叠，可复制成表格或存 PDF 发回。
- 远程指令的回信里不写密送给了谁。
- V0.3.0：打包清单的「已打包 / 有问题」改成二选一，生成结果前检查漏勾；打印 / 存 PDF 时订单号保留为链接；去掉不需要的「只有面单」合并 PDF；远程指令勾「开启」时自动检查并保存设置；邮件程序注册名改为中性的 `com.packhelper.mailer`，准备开源。
- V0.3.1：插件图标直接打开批次页（去掉弹出小窗口，所有操作都在批次页完成）；手动添加订单挪到批次页，可以选包裹、平台，上传图片和面单。

### 阶段五：运行状况（V0.6.0）
- **掉线报警**：电脑睡眠 / 断电时扩展自己什么都发不出去，只能由外部监控服务（healthchecks.io 之类，「超过 N 分钟没收到心跳就报警」）来发现。`lib/health.js` 用 `chrome.alarms` 每 1～15 分钟 GET 一次用户填的心跳网址（只允许 https，不带 cookie），结果记在 `heartbeatLast`。
- **每日登录检查**：`chrome.alarms` 在每天设定时间触发（`when` = 下一个 HH:MM，`periodInMinutes` = 1440），在后台依次打开三个平台的待发货列表，等 3.5 秒看地址有没有跳到 login / sign-in / auth；需要重新登录就通过现有的 Native Messaging 邮件程序发提醒（不带附件）。一键拉取 / 远程指令运行中时推迟 15 分钟（只补一次）。没有做「快过期提前提醒」：平台不告诉剩余时间，按 cookie 估算需要新权限而且不准。
- **诊断页面** `diag.html`：只读已有的记录（`lastScan`、`lastRun`、`lastMail`、`remoteLastPoll`、`remoteLog`、批次里缺面单的订单）和新的 `heartbeatLast` / `loginCheckLog`，整理逻辑在纯函数 `lib/diag.js`。导出前邮箱打码、心跳网址只留路径前 4 位，暗号不导出。导出用 `chrome.downloads`（`<a download>` 配中文文件名在部分环境会变成「download」）。
- 测试：Playwright + 本地 HTTPS 模拟平台（Poshmark 跳登录页）和心跳服务；邮件程序按真实方式注册成 Native Messaging host（`<user-data-dir>/NativeMessagingHosts/`），用 `PACKHELPER_FAKE_SMTP` 把邮件存成 .eml 核对。Linux 无头 Chromium 要设 `LANG=C.UTF-8`，否则 `chrome.downloads` 拒绝中文文件名。

### 阶段七：首页和功能模块（V0.7.0）
- 问题：批次页越来越长，拉取、批次表格和十几项设置挤在一页；而且自己定制的功能（比如售出同步）要改好几个共用文件，公开版一更新就要合并冲突。
- 做法：仍然是**同一个页面**（`batch.html`），所有按钮和输入框的 id 不变，`batch.js` 里的业务逻辑基本没动，只在外面加一层外壳 `core/shell.js`：按地址（`#/shipping/pull`、`#/settings/mail`……）切换显示哪一块。这样拉取、打包、远程指令这些已经在真实平台上跑稳的流程不受影响。旧地址 `#run`、`#remote`（远程指令、一键拉取自动打开）照旧可用，显示在「发货 → 拉取订单」。
- 模块：`core/registry.js` 登记模块说明（名称、图标、简介、`status()`、`todos()`、`mount()`、`panes`），首页卡片、「需要处理」、功能管理都由它生成；内置三个模块在 `modules/`。私有模块放 `modules-private/`：公开版里只有两个空清单（`index.js` 页面部分、`background.js` 后台部分），私有仓库 = 公开版 + 这个文件夹里的东西，合并公开版更新不会冲突。外壳单独 `import()` 私有清单，出错时首页照样能用并提示。后台部分登记 `{ id, alarms, messages, schedule, watch }`，`background.js` 统一分发，模块被关掉时清掉它的定时器。
- 「需要处理」复用 `lib/diag.js` 的状态计算（和诊断页同一套判断），不另写一套。
- 关掉模块：`settings.modules.<id> = false`；后台 `scheduleRemotePolling` / `scheduleHeartbeat` / `scheduleLoginCheck` 用 `moduleOn()` 判断，设置变化时重新排定时任务。
- 测试：Playwright 加载扩展，逐页检查路由、中英文（英文模式下扫一遍页面上残留的中文）、邮件设置保存、远程指令开启校验和定时任务、模块开关（定时任务清掉 / 恢复、首页卡片消失、地址回首页）、手动加订单后首页的「缺面单」提醒、`#run` 旧地址拉取后自动切到批次、私有模块的卡片 / 页面 / 往运行监控加子页面。

### 阶段八：Whatnot（V0.8.0～V0.8.6）
- Whatnot 的特点：**每件商品是一个单独的订单**（Order #…），同一买家的多件会自动合进同一个包裹（Shipment #…），整个包裹最后生成一张面单。所以发货助手里「订单号」用包裹号，包裹里每件一行（各自的 Order # 存在 `itemOrderNo`），共用一张面单（编号 W）。
- 读取：Seller Hub → Shipments（`/dashboard/shipments`）。表格每行 `tr[data-testid="shipments-<base64>-row"]`，base64 解出来是 `ShipmentNode:<包裹号>`；状态在「Status」列（Needs Label / Ready to Ship / Delivered …，已寄出 / 送达 / 取消的跳过）。逐个打开 `/dashboard/shipments/<base64>`，右边详情栏 `[data-testid="shipment-details-sidebar"]` 里每件商品 = 一个「Order #…」链接所在的区块（图片 alt 是完整标题）。先核对详情栏头部的 `#包裹号`，防止读错包裹。代码在 `lib/whatnot.js`。
- 面单：只下载已经生成好的——详情栏里的「Print Shipping Label」是指向 S3 PDF 的链接。这个 PDF **前面是 Whatnot 的 packing slip、最后一页是面单**：`splitWhatnotLabel` 逐页读文字，带「Whatnot Packing Slip」的是 slip 页（拿来读 SKU），其余是面单页，打印文件只放面单。「Generate Label」「Generate New Label」「Mark Package as Shipped」绝不点：生成后包裹不能再合并同一买家后来的订单，重量尺寸也需要人确认；Needs Label 的包裹标缺面单并写明原因。
- SKU：① 标题方括号 ② 已生成面单的从面单 PDF 里的 slip 页读；还没生成的点「Generate Packing Slip」读（slip 可能是弹窗、新标签页、网页生成的 PDF 或下载的 PDF，几种都试）③ SKU 记忆。slip 里每件写「Order 订单号」+「SKU …」，按订单号对应到每件商品。PDF 文字用 `DecompressionStream` 解压内容流，**每个字体用自己的 ToUnicode 表**（混用会乱码）。
- slip 标签页：Whatnot 从后台标签页打开 slip 时，Chrome 记下的「来源标签页」是当时在前台的那个，不是包裹页，所以按网址认（`whatnot-shipping-pdf…/packing_slips/`）；只关这次点出来的那一个，没读到时再等 20 秒关晚开的那一个，不碰用户手动打开的。售出同步里 slip 读不到的隔 3 小时再试、最多 3 次，避免每轮都生成新 slip。
- 缺面单的包裹：发货包里有「打印-packing slip（缺面单）.pdf」，每个包裹一张和对照卡同格式的卡（`drawCards(…, { slip: true })`：「订单 #…」、Whatnot 每件下面「Order #…」、底部「还没有面单：先拣货装袋，袋上写 W02」）。官方 slip 不放进发货包（有价格和地址）。
- 测试：用保存下来的真实 Shipments 页面（两件合包 + 单件、Needs Label + Ready to Ship）、真实 slip 和真实面单 PDF 做本地模拟。

## 4. 测试方法

所有功能都在本地用 Playwright + 真实 Chromium（加载扩展）+ 本地 HTTPS 模拟服务器（`--host-resolver-rules` 把平台域名指到本机）做端到端测试：模拟 Poshmark 订单页和下载弹窗、Depop 列表和 blob 下载、Mercari 订单页 / 商品页；邮件程序用 `PACKHELPER_FAKE_SMTP`（把邮件存成 .eml）和 `PACKHELPER_FAKE_IMAP`（目录里的 .eml 当收件箱）测试，不会真的发信。真实平台上的效果以实际拉取为准。
